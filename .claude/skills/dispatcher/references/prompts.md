# 子への指示の雛形

`<...>` を埋めて使う。子は日本語で指示を受け、PR の説明も日本語で書く（変更メモ `changelog.d/` の言葉はゲームの決まりに従う）。

## 起動（新しい issue）

```
<owner>/<repo> の issue #<N>「<題>」を進めてください。issue の本文とコメント、<関係する設計書・親 issue・前の PR>、
`docs/ROADMAP.md`（読むだけ）を読んでから始めてください。

**持ち主の方針**   ← 関係するレーンのときだけ入れる（UI/UX の参考、世界観、用語など）
- <方針>

**進め方**
- <この issue に固有のこと：設計書の節、完了条件、測るもの、など>
- 持ち主が決めないと進めない事柄だけを「持ち主の判断待ち」に書く。後回しにできる判断は、推しの案で進めて needs-decision の issue を立てる
  （本文の最後に `---` と `_Generated by [Claude Code](https://claude.ai/code)_`）。PR の説明には「決めたこと（あとで変えられる）」として書く。
- 必須チェック `<必須チェック>` が緑、main が最新、判断待ちがない PR は、配り役がマージします。

**並行して動いている子・PR**
- <同時に動いている子と、ぶつかりそうなファイル。どちらが後から合わせるか（先にマージされたら取り込んで直す、など）>
- セーブの版・入力の割り当て・Autoload などがほかの子と重なったら、後から入るほうが振り直す。
- main にマージがあったら取り込む（merge。rebase しない）。

**決まり**（CLAUDE.md も必ず読むこと）
- PR を出す前に CLAUDE.md の検証をすべて通す（`node tests/run.mjs` を通す）。
- `docs/ROADMAP.md` のチェックは編集しない。測った数字は PR の説明に書く。
- `changelog.d/<added|changed|fixed|removed|internal>/<名前>.md` にメモを置く（CI・ツールは internal）。
- 共有ファイル（<このゲームの共有ファイル>）は追記だけにする。
- `.github/workflows/` は CI の issue でなければ触らない（触るなら Actions を full SHA で固定し、`bash tools/ci/check-workflows.sh` を通す）。
- PR は main に向けて出し、本文に `Closes #<N>` を書く。見た目が変わるなら前後のスクリーンショットを載せる。
  PR を出したら `subscribe_pr_activity` で見張り、CI が緑になるまで直す。マージはしない。

**利用量を抑えるための約束**
- `<必須チェック>` が緑になり、PR の説明が今の状態に合ったら、`unsubscribe_pr_activity` して止まる。自分で定期チェック（`send_later` など）は入れない。
  入れてあれば消す。マージまでの見張りは配り役が行い、main との衝突や CI の赤があれば配り役が起こす。
- main を取り込むだけで衝突がないときは、手元での全部の検証は省き、push して CI に任せる。
  衝突を解いた・結果の表を貼り直した・セーブの版を振り直したときは、速いテストだけ手元で通してから push する
  （E2E の全件は、画面やスクリプトの衝突を解いたときだけ手元で回す）。
```

レーンごとの足し方：
- **ゲームの仕組み**：試合や進行の結果が変わるなら、前後の結果（勝敗・時間・測った数字）を PR に書く。
- **needs-decision の issue**：案を 2〜3 つ比べ、推しの案で実装まで進めてよい。
- **CI・ツール**：新しいジョブは必須チェックが待つ先に入れる。CI の時間の前後を書く。pull_request_target は使わない。
- **ドキュメントのまとめ**（配り役がときどき起動する）：前回のまとめの PR から今までにマージされた PR を `git log --merges` と各 PR の説明で確かめ、
  `docs/ROADMAP.md` のチェック・結果の行・レーンの表・決定待ちの一覧を今の main に合わせる。数字は PR の説明から写し、測り直さない。

## 起こす（main と衝突した PR）

```
配り役から：PR #<P> は main と衝突しています。その後に main に入ったもの：<PR 番号と中身、衝突しそうな所>。
origin/main を merge で取り込み（rebase しない）、両方の機能が残るように解いてください。
検証は「利用量を抑えるための約束」のとおり（表の貼り直しや衝突を解いたなら速いテスト、画面の衝突なら E2E も）にして push し、
`<必須チェック>` が緑になったら PR の説明を今の状態に合わせ、`unsubscribe_pr_activity` して止まってください（定期チェックは入れない）。判断待ちがなければ配り役がマージします。
```

## 起こす（セッションの上限で止まっていた）

```
配り役から：セッションの上限で止まっていたので再開してください。<止まる前にしていたことと、その後に main に入ったもの>。
<続きの指示>。PR の説明は今の状態に合わせる。
```

## 起こす（CI が赤）

```
配り役から：PR #<P> の <チェック名> が <head SHA> で落ちています（<分かった原因、ログの一行>）。
root cause を直して push してください（テストを飛ばす・弱めるのは不可。遅い CI の runner でも通るように）。
```

## 方針が変わったとき（動いている子すべてへ）

```
配り役から（持ち主の決定、進め方の変更）：<新しい方針>。
<子にとって何が変わるか：PR の説明の書き方、判断待ちの扱い、など>。
```

## 定期チェック（send_later で自分へ）

```
配り役の定期チェック（<時刻>Z）。scratchpad の dispatch-state.md を読み、次を行う：
1. 通知を読む（ReadNotifications）。開いている PR（<PR 番号>、ほか <作業中の子の issue> の子が出した新しい PR）を subscribe し、状態を見る。
2. 自動マージ：`<必須チェック>` 緑・main 最新（遅れていれば Release コミットのあとに update_pull_request_branch、衝突なら子を起こす）・
   「持ち主の判断待ち」なし・PR の説明に未記入なし・未解決スレッドなし → merge commit で 1 本ずつ。
3. 子がセッション上限などで failed なら create_trigger(persistent_session_id) で起こす。
4. 働いている子（PR 待ちは数えない）が上限より少なければ次を起動：<次の候補と、その前提>。
5. dispatch-state.md に記録し、次のチェックを 1 時間後に send_later で入れる（変化なしが 3 回続いたら止める）。
```
