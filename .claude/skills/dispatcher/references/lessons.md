# 並行作業でぶつかった所と、その避け方

このテンプレートから作ったゲーム（sfrts）で実際に起きたことから。ゲームで新しく学んだことがあれば、そのゲームのこのファイルに足す
（どのゲームにも効くものはテンプレートにも戻す）。

## main が赤くなった（意味の衝突）
- 別々には緑だった 2 本の PR が、両方入った main で落ちた（同じ仕組みの予算を 2 本が別々に変えた、網羅テストが入ったあとで
  もう 1 本が対象のクラスに欄を足した、など）。
  → 同じレーンで同じ仕組みを触る項目は、前の PR がマージされてから次を起動する。
  → ルールセットを「必須チェック＋枝が最新」にする（マージキューは個人の private リポジトリでは使えない）。
  配り役は 1 本ずつマージし、次の PR は Release コミットのあとの main で CI を回し直してからマージする。
- main が赤いあいだは、ほかの PR の CI も同じ所で落ちる。直す PR を最初にマージし、それまでほかはマージしない。

## 子どうしで同じ番号・同じ場所を取り合う
- **セーブの版**：2 本が同時に同じ番号へ上げた。後から入る側に次の番号へ振り直させる。
- **コマンドの種類・キーの割り当て**：2 本が同じキーを使った。後から入る側が変える。
- **同じ定義に同じ欄**：2 本が別々に同じ欄を足した。後から入る側が先の形に合わせる。
- **メニューの枠など番号付きの場所**：配り役が先に割り振る。
- **HUD などの大きなスクリプト**：UI の子が何本も触り、マージのたびに衝突した。
  → UI の子は同時に 2〜3 本までにし、ほかの子には「追記だけ」と伝える。先に入ったもののあとに、残りの子を順に起こす。
- **決定性のテストの期待値の表**：結果を変える PR はどれも表を貼り替える。先に入ったものがあれば、後の子は main を取り込んで貼り直す。
  プロンプトの「並行して動いている子」に必ず書く。
- **新しい状態のセーブ**：同時に 2 本が状態を足すときは、セーブへの追加は後から入る側が行う。

## 子が止まる
- **PR のコメントでは、止まっている子は起きない。** `create_trigger`（`persistent_session_id`＋`run_once_at` 1〜3 分後）で起こす。
- **セッションの上限**：`get_session` で `status_bucket: FAILED`、`status_detail: "You've hit your session limit"`。
  上限の戻る時刻を過ぎたら起こす。3 時間止まっていたのに、配り役が気づくまで PR が衝突のままだったことがある。
  → 定期チェックでは、PR を見るだけでなく、子の状態を `get_session` で見る。

## CI
- **遅い runner**：実時間に頼る E2E（「3 倍速が実時間より速く進む」など）が CI の遅い runner で落ちた。
  runner の速さに頼らないテストに直させる。「フレーク」として再実行で済ませない。
- **キャンセルされた run**：新しい push で置き換わった run は失敗に見える。head の SHA を確かめる。
- **わざと落とす試し**：CI が見つけるかを確かめるために落ちる変更を push し、次の push で戻す子がいる。
  head のコミットの件名（"TRIAL (reverted next)" など）を見て、待つ。
- ドキュメントだけの PR で重いジョブを飛ばす仕組みがあるなら、ドキュメントの子にはローカルのビルドを求めない。

## 積み上げ（stacking）
- 前の PR にしか無い部品を使う項目は、前の PR の枝を `source_revision` にして起動し、PR の base をその枝にさせる
  （CI の `pull_request:` が枝を絞っていなければ CI は回る）。
- 前の PR がマージされたら base を main に付け替え（GitHub が自動でしない場合は `update_pull_request` で）、子に main を取り込ませる。
- 複数の PR に依るものは、最後の 1 本以外がマージされてから、その 1 本に積む。

## 配り役自身の作業枝
- 配り役の作業枝に `git pull origin main` しない（枝が main に進み、未 push のコミットに見える）。`git fetch` と `origin/main` を使う。
- 配り役の作業枝の PR がマージ済みなら、`git checkout -B <枝> origin/main` で作り直してから次の変更を載せる。

## issue の番号と ID
- ID（`U7` など）が別の issue と重なったことがある。立てる前にレーンの表と開いている issue を検索する。
- 設計書の中の仮の ID は、立てるときに振り直す。

## 利用量
- 自動マージ・同時 5 本にしてから、1 時間あたりのマージは 2.4 → 2.8 本に増えたが、子 1 本の費用（API 換算で約 $11〜14）はほぼ同じだった。
  減りが速く見えたのは、子がレビュー待ちで止まらなくなったため。
- 無駄になっていたのは次の 3 つ：
  - 配り役の文脈が約 30 万トークンまで育ち、何もしなくてよい通知や CI の確認のたびに読み直していた（配り役だけで全体の 1 割強）。
    → 文脈が大きくなったら新しい配り役に引き継ぐ（SKILL.md §9）。
  - 子が PR を出したあとも 1 時間ごとに自分で起きて確認していた（子の文脈も 40 万トークン前後）。
    → 緑になったら見張りをやめて止まり、配り役が必要なときだけ起こす。
  - main との衝突や表の貼り直しのたびに、子が手元で全部の検証（E2E・Web エクスポート）をやり直していた（1 本で 4 回以上、約 $28）。
    → 衝突のない取り込みは CI に任せ、表の貼り直しは速いテストだけ手元で回す。
