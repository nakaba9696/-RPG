# 下準備から始めるまで

配り役を初めて動かすときの手順。上から順に行う。
「持ち主」はリポジトリの持ち主（人）、「配り役」はこのスキルで動く Claude のセッション。

## 1. GitHub とクラウドの環境（持ち主が一度だけ）
1. **Claude の GitHub App** をリポジトリに入れ、claude.ai で GitHub をつなぐ（配り役と子が issue・PR・コメントを扱うため）。
2. **Claude Code on the web の環境**を 1 つ作る（claude.ai/code。README の「Claude Code cloud で使う」）。
   - リポジトリ：このゲームのリポジトリ
   - ネットワーク：godot（github.com のリリース）と、ゲームが使うもの（npm など）が取れること
   - セットアップスクリプト：`tools/cloud/setup-env.sh` の中身を貼る（`godot` を入れる）。
     貼らなくても `.claude/settings.json` の SessionStart フックが同じものを走らせるが、毎回時間がかかる。
   - 子はこの環境を受け継ぐ（`create_session` で `environment_id` を省くと、配り役と同じ環境になる）。
3. **子の考える深さ**（任意）：`.claude/settings.json` に `"effortLevel": "high"` を足す。子は main から始まるので、main に入っている必要がある。
   モデルは `create_session` の `model` で渡す（持ち主が決める）。

## 2. CI とマージの守り（持ち主が一度だけ）
並行して出る PR が main で組み合わさって落ちないようにする。
1. **必須チェックを 1 つ決める**。テンプレートの `build.yml` なら Web のビルド（`build / build`。`security` のあとに走る）。
   ゲームが CI のジョブを足したら、全部を `needs` に持つまとめのジョブ（例 `CI result`：どれかが失敗か取り消しなら落ちる）を作り、
   それだけを必須にすると、ジョブが増えても設定を直さずに済む。
2. release.yml が main に Release コミットを push するため、fine-grained PAT を environment `main` の secret **`RELEASE_TOKEN`** に置く
   （README の「バージョン番号と変更履歴」）。
3. **ルールセット**（Settings → Rules → Rulesets、default branch）：
   - Bypass list に `RELEASE_TOKEN` の PAT の持ち主。
   - **Require status checks to pass** に 1 の必須チェック。
   - マージキューが使えない（個人の非公開リポジトリ）なら **Require branches to be up to date before merging をオン**。
     これで「main が最新でない PR」はマージできなくなり、配り役は SKILL.md §4 の順（1 本ずつ、Release のあとに次を更新）でマージする。
   - 非公開リポジトリでルールセットを使うには GitHub Pro 以上が要る。

## 3. ラベル（配り役が作ってよい）
- レーンごとの `lane:<X>`（`docs/ROADMAP.md` のレーンの表に合わせる）。
- `needs-decision`：名前・数値・見た目・遊び比べなど、持ち主が決めることが残る項目。

## 4. 作業の分け方を main に入れる（配り役が PR、持ち主がマージ）
子は main から始まるので、分け方の文書が main に無いと子が読めない。
1. `docs/ROADMAP.md` に「並行作業の単位」の節を書く：
   - **レーン**（例 C：コア・M：仕組み・A：AI・V：見た目・U：UI・T：CI とツール・D：設計書 など。ゲームに合わせて決める）
   - レーンごとに**書き換えてよいファイル（関数）**。同じレーンの中は順番に、別のレーンは同時に。
   - 項目ごとの**前提**（同じレーンの前の項目か、他のレーンの項目）と**波**（同時に始められる組）。
   - **衝突を避けるための約束**：共有ファイルは追記だけ、セーブの版やキーの割り当ては後から入る側が振り直す、など（[lessons.md](lessons.md)）。
   - 大きく書き換える項目は単独の期間を取る。
2. PR を作ってよいか持ち主に聞き、マージされるまで子を起動しない。

## 5. issue を立てる（件数と中身を持ち主に確かめてから）
1. 既にある issue を検索し、重複を作らない。ID（`U7` など）も重ねない。
2. **親 issue**：本文に依存グラフ（Mermaid の `graph LR`）と波の表。
3. **項目ごとの issue**（親のサブ issue にする：`sub_issue_write`）。本文に書くこと：
   - レーン・内容
   - **触ってよいところ／触らないところ**（ROADMAP のレーンの表と「衝突を避けるための約束」から）
   - 前提：`Blocked by #N`（GitHub の正式な依存はツールで結べないので、本文を正本にする）
   - 完了条件
   - 検証の手順（CLAUDE.md のもの。少なくともヘッドレスの `--import` と Web エクスポート）
   - 決まり：`docs/ROADMAP.md` のチェックは編集しない（数字は PR の説明へ）、`changelog.d/` にメモ、`Closes #N`
   - 最後に `---` と `_Generated by [Claude Code](https://claude.ai/code)_`
4. ラベル：`lane:<X>`、持ち主が決めることが残るものは `needs-decision`。

## 6. 配り役のセッションを始める
Claude Code on the web で、上の環境・このリポジトリの新しいセッションを開き、次のように頼む
（権限のモードは auto が楽。子は配り役のモードより広くならない）：

```
/dispatcher を使って、<owner>/<repo> のロードマップの配り役をして。
- 同時に働く子：5 本（PR 待ちは数えない）
- モデル：<モデル>
- マージ：残件がなく CI が通ったものは配り役がマージしてよい（1 本ずつ）
- 後回しにできる判断は needs-decision の issue にして先へ進める
- 1 時間ごとに状況を確かめ、変化があったら報告
まず今の状態（開いている PR・issue・動いている子）を確かめて、計画と確認事項だけを出して。
```

最初の返事では、配り役は計画と確認事項（PR を作るか・issue の件数とラベル・同時に動かす本数・マージを任せるか）だけを出し、
持ち主の答えを待ってから issue を立て、子を起動する。
自動マージを任せない場合は、SKILL.md §4 の「マージ」を「持ち主に、マージしてよい PR と順番を知らせる」に読み替える。

## 7. 回し始めたら
SKILL.md の §0（状態ファイル）→ §3（起動）→ §4（マージ）→ §5（起こす）→ §6（定期チェック）を繰り返す。
いくつかの issue が閉じるたびに「ドキュメントのまとめ」の子を起動し、ROADMAP のチェックを 1 本の PR で追いつかせる
（雛形は [prompts.md](prompts.md)）。
